# 决策记录

## 2026-08-06：MVP1.1 补个人用户系统，采用用户名密码登录

结论：在 Demo User 写作闭环跑通后，MVP1.1 补真实个人用户系统。注册登录采用用户名 + 密码，开放注册，不做邀请码；登录态使用 7 天有效的 HTTP-only Cookie。未登录用户可以预览工作台 UI，但任何创建或访问用户资产的动作都必须登录。手机号在注册后通过账号设置绑定，验证码先做假发送；手机号找回密码只预留入口和接口边界。

理由：

- 用户名密码比手机号短信、邮箱验证、第三方登录更适合快速迭代。
- 未登录可看工作台可以降低理解成本，但不创建游客数据，避免素材和风格归属复杂化。
- 业务接口必须从当前登录用户获取 `user_id`，不能继续 fallback 到 Demo User，否则会产生数据串号风险。
- 手机号绑定提前预留找回密码路径，但不接真实短信服务，避免扩大首轮实现范围。
- 本轮只做注册登录和数据绑定，不新增组织、余额、历史文章列表等新业务功能。

## 2026-08-05：MVP1 收窄为 Demo User + 个人风格库写作闭环

结论：MVP1 不做真实个人注册登录、组织注册、组织子账号、组织共享余额、充值和扣费。首版使用固定 Demo User，保留 `user_id` 数据边界，先打通“上传多篇相似作品 → 风格分析草案 → 用户编辑/命名/确认 → 保存到个人风格库 → 选择风格生成文章 → 按自然段重写”的核心闭环。

理由：
- 当前最大风险是风格写作闭环是否成立，不是账号、组织和余额复杂度。
- 所有核心数据表保留 `user_id`，后续补真实注册和组织模型时不需要重写作品、风格和文档主链路。
- PostgreSQL 作为正式数据层目标；本地开发允许 SQLite fallback 方便验证。
- 余额和组织商业化能力放到 MVP2，避免拖慢作品上传、风格确认和写作体验验证。

## 2026-08-06：段落重写采用弹窗交互，风格删除采用软删除

结论：MVP1 的文章段落重写不再在每个自然段下方常驻输入框，而是保持正文连续阅读形态，通过自然段 hover 高亮和弹窗提交修改意见。已保存风格支持删除，但使用软删除：删除后不再出现在风格库，也不能用于新写作；历史已生成文章不受影响。

理由：

- 常驻段落输入框会把文章切得过碎，影响用户判断全文整体效果。
- hover 高亮 + 弹窗能把“阅读正文”和“修改某段”分开，降低页面噪音。
- 软删除保留审计和历史关联，避免删除风格后破坏既有写作任务、成本记录或文档展示。
- 后续如果增加回收站、恢复风格或操作审计，软删除模型可以直接扩展。

## 2026-08-04：不使用 Dify 作为生产核心

结论：正式公网收费产品采用自研 SaaS 应用层，Dify 只可作为内部原型或运营工具。

理由：

- 账号、套餐、支付、额度、退款和对账必须由业务系统掌握。
- 用户素材和风格档案涉及隐私、授权、删除和导出。
- 写作任务需要版本、审计、失败恢复和成本追踪。
- 后续需要跨模型供应商切换，不能把状态锁进低代码流程。

## 2026-08-04：首发采用阿里云方案

结论：面向中国大陆用户时，首选阿里云百炼/Qwen + FC + RDS PostgreSQL/pgvector + OSS + CDN + WAF。

理由：

- 国内访问和备案链路更顺。
- 百炼/Qwen 适合中文写作作为首轮盲测对象。
- RDS PostgreSQL + pgvector 足够支撑 MVP，不需要一开始引入独立向量数据库。
- FC 可以降低早期运维成本，稳定后再评估 ACK/ECS。

## 2026-08-04：首版不做微调

结论：先用结构化风格档案 + RAG + 用户反馈。

理由：

- 用户早期素材量不足。
- 微调成本、授权、删除权和数据血缘复杂。
- RAG 更容易解释、回滚和调试。
- 真实“生成稿到用户修改稿”数据比单纯原文更适合后续训练。

## 2026-08-04：MVP 首发形态为个人写作 SaaS

结论：首发形态是个人写作 SaaS 平台。作家协会等组织只是 Organization/Tenant 场景，组织可以开通权限并在组织下开设个人账户；真正使用风格写作能力的是组织内的个人 User/Writer。

理由：

- 产品核心仍是个人风格写作，不是只服务某个作协的一次性定制系统。
- 组织账号模型可以兼容作协、机构、工作室和未来团队版。
- 数据隔离、额度管理和权限分配可以统一落在 Tenant 模型上。

## 2026-08-04：MVP 不真实收费，但必须做虚拟额度

结论：MVP 阶段不接真实支付，不做真实收费；但必须实现 Virtual Credit 和 Credit Ledger。

理由：

- 虚拟额度能提前验证任务预估、冻结、结算、失败释放和成本记录。
- 后续接支付宝/微信支付时，不需要重写核心额度逻辑。
- 能限制内测用户滥用，保护模型成本。

## 2026-08-04：用户数据默认私有且不参与训练

结论：用户 Material、Document Version 和反馈数据默认私有，不参与训练。未来 Personal LoRA 是单独收费能力，必须单独授权、单独训练、单独计费。

理由：

- 降低 MVP 合规和信任风险。
- 保留未来个性化训练商业化空间。
- 删除权、授权撤回和训练数据血缘可以在后续 Personal LoRA 设计中单独处理。

## 2026-08-04：爬虫只作为授权样本采集器

结论：MVP 可以使用爬虫辅助采集作者样本，但只允许采集自有、授权、开放许可或公共领域来源。未授权现代作者作品不得进入 RAG、评测集、Prompt 示例库、训练集或对外演示环境。

理由：

- 个人风格写作产品最终会放到公网，且未来收费，样本来源必须可审计。
- 文字作品受著作权保护，公开可访问不等于可复制、汇编、改编或用于商业 AI 服务。
- MVP 的评测价值来自可复现和可解释，缺少授权与用途元数据的样本不能作为可靠评测资产。
- 后续 Personal LoRA 需要单独授权，不能把 MVP RAG/评测授权自动扩展为训练授权。

## 2026-08-05：先建立可审计评测 harness 再进入工程骨架

结论：MVP 进入 Next.js/FastAPI 工程实现前，先使用 `eval_sets/mvp_style_eval_v1/` 管理评测清单、任务、生成记录、盲评评分、复制检测和复盘结论。

理由：

- 个人风格写作的核心风险是效果不可验证，必须先固定对照组、评分口径和通过门槛。
- 评测记录需要保留 material、prompt、retrieval、generation、score 和 copying report 的血缘，后续才能定位风格失败、复制风险和成本问题。
- 注：关于现有 `测评集/网页作品` 的内部使用范围，已由 2026-08-05 “内部评测材料跳过授权审查”决策覆盖。
- `Style Profile + RAG` 是否优于普通直出，需要通过 `baseline_direct`、`style_prompt_only`、`style_profile_rag` 的盲测结果判断。

## 2026-08-05：内部评测材料跳过授权审查

结论：当前 `测评集/网页作品` 材料按内部评测和内部 RAG 实验材料处理，不做授权审查流程；默认允许进入 `eval` 和内部 RAG 对照实验，但不默认允许训练。

理由：

- 当前目标是验证产品技术假设，不是对外演示、商业宣传或公开发布数据集。
- 授权审查会阻塞第一轮效果验证，且用户已明确当前材料内部使用、不涉及授权问题。
- 训练、微调和公网商业化仍是单独决策，不能从“内部评测可用”自动外推。

## 2026-08-05：第一轮 LLM 自动盲评未完全通过 MVP 开发门槛

结论：第一轮 `baseline_direct` / `style_prompt_only` / `style_profile_rag` 三组对照已完成 40 个任务、120 条输出、120 条 LLM 盲评分数和复制风险检查。`style_profile_rag` 明显优于 `baseline_direct`，但未达到“偏好胜率 >= 60%”门槛，且整体没有稳定胜过 `style_prompt_only`。因此暂不把 `Style Profile + RAG` 作为已验证核心能力直接进入 MVP 工程开发。

关键数据：

- `style_profile_rag` 相对 `baseline_direct` 的平均风格分提升：+1.400。
- `style_profile_rag` 对 `baseline_direct` 的风格分更高：28/40；非劣率：70%。
- `style_profile_rag` 可用或编辑后可用：39/40。
- `style_profile_rag` winner/tie count：15/40，低于 60% 门槛。
- `style_prompt_only` winner/tie count：19/40，高于 `style_profile_rag`。
- 复制风险：120 条全部 `none`，无 medium/high incident。

理由：

- RAG 当前证明了“比直出更接近风格”，但还没有证明“比结构化风格 Prompt 更值得进入首版复杂工程”。
- `style_profile_rag` 可能存在检索证据噪声、注入信息过多、Prompt 过载或风格档案约束被片段稀释的问题。
- 下一步应先复盘输分样本并做第二轮最小改进；如果第二轮仍不能稳定超过 `style_prompt_only`，MVP 可降级为 `style_prompt_only + 可编辑 Style Profile`，RAG 延后。

## 2026-08-05：第二轮 RAG v2 仍未超过 style_prompt_only，MVP 默认路径改为 Style Profile Prompt

结论：第二轮针对第一轮中 RAG 输给 prompt-only 的 20 个任务，新增 `style_profile_rag_v2`，采用低数量、体裁感知、机制证据式 RAG。结果显示 v2 明显优于 RAG v1，但仍未稳定超过 `style_prompt_only`。因此 MVP 首版默认生成路径调整为 `style_prompt_only + 可编辑 Style Profile`；RAG 只作为文章/散文实验增强，不作为小说/诗歌默认路径。

关键数据：

- 第二轮覆盖：20 个失败样本、60 条盲评分数。
- `style_profile_rag_v2` 对 RAG v1 平均总分提升：+2.750。
- `style_profile_rag_v2` 高于 RAG v1：14/20。
- `style_profile_rag_v2` 对 prompt-only 平均总分差：-0.200。
- `style_profile_rag_v2` 高于 prompt-only：9/20；非劣率：45%。
- `style_profile_rag_v2` winner/tie count：8/20，低于 60% 门槛。
- `style_profile_rag_v2` 复制风险：20/20 为 `none`。

体裁判断：

- 文章：v2 明显有效，可作为后续 RAG 灰度方向。
- 散文：v2 有效，但样本数较小，需要后续确认。
- 小说章节：v2 有修复，但仍不稳定。
- 诗歌：v2 未解决，RAG 仍有拖累。

理由：

- 两轮评测都说明，结构化 Style Profile 已经提供了主要风格收益。
- RAG 增加了检索、证据选择、上下文压缩和复制风险控制复杂度，但当前没有提供足够稳定的额外收益。
- 首版 MVP 应优先验证用户是否愿意使用、编辑并保存个人 Style Profile，而不是把技术复杂度押在尚未稳定的 RAG 上。
- RAG 不删除，只降级为可插拔增强能力，等有用户修改稿和真实反馈后再重做检索策略。

## 2026-08-17：起草平台《隐私政策》与《用户协议》

结论：为墨小小个人风格写作 Agent SaaS 起草两份对外法律文本，存放于 `10_legal_法律协议/`：`隐私政策.md`、`用户协议.md`。文本以中国大陆法律框架（含《个人信息保护法》《生成式人工智能服务管理暂行办法》《著作权法》）为准，落地了以下既有合规决策：用户素材与风格档案默认不用于训练（对应 2026-08-04 决策）、第三方模型供应商（千问等）调用时传输必要内容、RAG 仅实验增强、MVP 虚拟额度 / MVP2 真实支付分阶段说明、内容安全审核与 AI 生成内容标识、按用户 ID 数据隔离。

理由：

- 公网发布前必须具备隐私政策与用户协议，且内容须与产品设计一致，避免"协议与实现不符"的合规风险。
- 文本采用【运营主体全称】【注册地址】【隐私联系邮箱】【ICP 备案号】【生效日期】等占位符，待运营方补全；正式上线前应由律师复核。

注意：本文件不是法律意见，正式发布前须经执业律师审阅。

## 2026-08-17：法律协议接入注册/登录/页脚，并落库同意记录

结论：将 `10_legal_法律协议/` 下的《隐私政策》《用户协议》接入产品：注册弹窗强制勾选同意、登录不强制、页脚加「用户协议 / 隐私政策」链接、新增 `/legal/terms` 与 `/legal/privacy` 静态 Markdown 渲染页。注册时后端强校验 `agreed_terms`，未同意返回 422；同意后在 `user_consents` 表写入两条记录（terms / privacy，各带版本 v1.0 与 client_ip），作为已告知用户的证据。

理由：
- 公网发布前注册流程必须有可证明的同意留痕，否则出争议时无法举证用户已被告知。
- 登录不强制勾选，降低老用户登录摩擦；但注册必须强校验，因为这是同意发生的关键时刻。
- 协议页采用前端静态 Markdown 渲染（零新增 npm 依赖，聚焦子集渲染器），避免引入重型 markdown 库；内容从 `apps/web/content/legal/` 读取，与 `10_legal_法律协议/` 同源维护。
- 同意记录入库而非仅前端勾选：前端禁用按钮只是体验层，后端 422 才是真正闸门；`user_consents` 表可追溯每次同意的版本与 IP，协议重大更新后重新确认时可追加记录。

实现要点：
- 后端 `UserConsent` 模型（`user_consents` 表），由 `Base.metadata.create_all` 自动建表，无需手写迁移。
- `auth_service.register_user` 增加 `agreed_terms` 必填参数与 `client_ip`，校验失败抛 422，成功后 `_record_consent` 写入两条记录（同一事务）。
- 前端 `AuthModal.tsx` 注册模式加勾选区与提交按钮禁用；`SiteFooter.tsx` 加协议链接；新增 `app/legal/[doc]/page.tsx` + `components/LegalDoc.tsx` + `lib/legal.ts` 解析器。
- 版本常量 `TERMS_VERSION` / `PRIVACY_VERSION = "v1.0"` 与两份文档生效版本一致。
