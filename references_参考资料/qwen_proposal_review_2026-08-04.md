# 千问方案对照评审

评审日期：2026-08-04

## 总体判断

千问方案适合作为“作家协会场景下的产品叙事和功能灵感”参考，但不能直接作为公网收费 SaaS 的实施方案。它对作家心理、创作工作台、风格诊断、RAG 基本逻辑讲得比较清楚；但对账号体系、支付、额度账本、租户隔离、审计、部署、安全、合规、模型成本和失败恢复没有展开。

本项目应吸收其中的产品表达和创作功能细节，但继续保持当前架构基线：自研 SaaS 应用层 + 云模型 API + 显式写作状态机 + 多租户 RAG。

## 值得吸收的内容

### 产品定位表达

千问提出“数字分身”或“灵感副驾驶”，并强调不是“代笔机器”。这对作家协会、严肃写作者和版权敏感用户很重要。

建议采纳为对外表达：

- 面向作家的个人风格创作助手。
- 辅助生成初稿、灵感扩写、润色改写。
- 用户掌握立意、情感和最终定稿权。
- 不宣传“一键替代作家”。

### 风格诊断模块

千问强调先上传 3-5 篇代表作，生成风格分析报告，再由作家确认或修正。这一点适合做首发体验。

建议落地为：

- 新用户可用 3-5 篇代表作启动风格诊断。
- 系统提示“素材越多，越稳定”，建议正式档案达到 8000 字以上。
- 风格报告必须可编辑，而不是一次性模型结论。

### 作家控制权

千问提出作家可能抵触 AI，因此 UI 应弱化聊天框属性，像 IDE 或专业写作软件。这与我们的 TipTap 编辑器方向一致。

建议加强：

- 第一屏是写作工作台，不是聊天页。
- 支持选中段落局部重写。
- 支持版本历史和差异对比。
- 支持用户修改风格规则。

### 多体裁功能细节

千问补充了几个值得进入 backlog 的功能：

- 小说：世界观、人物小传、情节大纲、分章节扩写、多角色对话。
- 散文：意象发散、情感基调迁移。
- 诗歌：格律检查、韵脚建议、断句与节奏模拟。
- 通用：普通白话文转个人文风、选中段落定向重写。

### “AI 味”负向约束

千问提出在 Prompt 中加入负向约束，避免高频 AI 套话。这个方向正确，但不应只靠固定禁词。

建议实现为：

- 平台级通用 AI 套话禁用表。
- 用户级禁用表达。
- 文体级失败模式。
- 风格审校模型输出结构化问题清单，再触发重写。

### 后续训练数据思路

千问提到 RLHF/反馈数据。首版不做 RLHF，但“用户评分和修改稿作为正负样本”应保留。

建议继续按本项目既定规则执行：默认不训练，只有用户明确授权后，才进入后续训练集。

## 不建议直接采纳的内容

### MVP 只选 1-2 位作家

作协定制项目可以这么做，但公网收费 SaaS 需要更宽的样本。建议第一阶段至少做 30-50 个任务评测，公测阶段 30-100 位种子用户。

### 第二阶段直接上 LoRA 微调

这一步过早。微调只有在 RAG + 风格档案 + 审校回路仍不能满足效果，而且有明确授权的高质量修改数据时才值得做。

### LangChain + LlamaIndex 作为默认生产编排

可以用于实验，但生产核心不建议把写作状态、计费和恢复逻辑藏进通用编排框架。首发应以自研显式状态机为主，只在文档解析或检索环节按需引入库。

### Milvus/Qdrant 作为 MVP 默认向量库

早期用户量和向量规模不明确时，RDS PostgreSQL + pgvector 更简单。Qdrant/Milvus 可作为后续扩展选项。

### 具体模型名写死

千问提到的模型名只能作为历史参考。实际开发必须以实施当天官方模型列表、计费、上下文长度和可用区为准，并通过模型配置表管理。

## 合并结论

将千问方案定位为“作协场景产品补充”，吸收以下内容进入项目：

- 产品话术：灵感副驾驶，不替代作家。
- 风格诊断：3-5 篇代表作可启动，但正式建议更多素材。
- 编辑器体验：弱聊天框，强化专业写作工作台。
- 文体功能：小说多角色对话、散文意象发散、诗歌格律/韵脚/节奏、局部重写。
- 风险控制：AI 味负向约束、作家控制权、版权水印作为后续能力。
