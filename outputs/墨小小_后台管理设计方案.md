# 墨小小 · 后台管理（Admin）设计方案

> 范围：业务方案 + 技术方案。目标是在「配置已入库、管理端 API 已落地但无 UI」的现状上，设计一套可运营的 SaaS 后台。
> 设计原则：**配置全部入库、代码不写死**（已落地）；**所有写操作可审计**；**敏感操作二次确认**；**先复用现有 API 做 MVP，再扩内容/成本/风控/运营**。

---

## 一、背景与现状

### 1.1 已实现（地基）
- **配置入库**：`membership_tiers`（等级/权益/月费）、`article_length_brackets`（长度档→积分）、`operation_costs`（固定操作积分）、`model_pricing`（模型单价，¥/百万 token）全部建表，代码只读不写死。
- **双账本**：用户侧 `points_balance`（按月懒重置）+ 内部 `cost_cny`（真实成本）。
- **受保护管理端 API**（`apps/api/app/admin_routes.py`，`require_admin`）：等级/档位/操作积分/模型单价 CRUD、用户列表与详情、手动调积分、全量用量记录查询。

### 1.2 数据模型（已存在，可直接被后台读取）
| 表 | 关键字段 | 后台用途 |
|---|---|---|
| `users` | `tier_id`/`points_balance`/`quota_period_end`/`is_admin`/`email`/`phone`/`status`(待扩) | 用户与账号管理 |
| `materials` | `user_id`/`title`/`genre`/`char_count` | 用户上传作品 |
| `style_profiles` | `user_id`/`name`/`status`/`is_default` | 风格档案 |
| `documents` | `user_id`/`style_profile_id`/`title`/`is_saved` | 生成文章 |
| `writing_tasks` | `user_id`/`status`/`model_name`/`tokens` | 写作任务 |
| `model_usage_logs` | `user_id`/`model_name`/`tokens`/`estimated_cost` | 成本核算 |
| `usage_records` | `user_id`/`op_type`/`points_consumed`/`cost_cny` | 积分消耗流水 |
| 4 张配置表 | 见上 | 套餐/档位/单价配置 |

### 1.3 缺口
- **无 UI**：管理端 API 无页面。
- **无聚合**：仪表盘所需的计数/汇总/趋势无端点。
- **无内容/风控/运营/财务**：素材、风格、文章、封禁、公告、优惠码、订单均无管理入口。
- **无审计**：写操作未留痕。

## 二、业务方案

### 2.1 功能全景（模块地图）

> 用户最初提的三块（会员账号 / 会员等级 / 每月积分与消耗）已标 ★。下面把它放进完整后台里，并补齐运营真正需要的能力。

| # | 模块 | 说明 | 优先级 |
|---|---|---|---|
| 1 | 概览仪表盘 | DAU/新增/生成量/积分消耗/成本/收入 一眼看全 | P0 |
| 2 ★ | 用户与账号管理 | 会员列表、搜索、详情、升降级、封禁、手动调积分 | P0 |
| 3 ★ | 会员等级与套餐 | 等级 CRUD、权益（下载/重写/长度上限/数量限制）、月费 | P0 |
| 4 ★ | 积分管理 | 每月积分额度、消耗流水、手动调整（带原因+审计） | P0 |
| 5 | 内容 / 风格管理 | 素材、风格档案、文章的查看、下架、删除 | P1 |
| 6 | 写作任务与文档 | 任务查询、文章检索、异常任务定位 | P1 |
| 7 | 成本管理 | 模型单价、token 成本、毛利率报表（按模型/时间） | P1 |
| 8 | 风控与内容审核 | 封禁/解封、举报队列、违规下架 | P1 |
| 9 | 系统配置 | 全局开关（注册开关/维护模式/默认等级）、参数 | P1 |
| 10 | 运营工具 | 站内公告、优惠码/邀请码、活动 | P2 |
| 11 | 财务与订阅 | 订单、续费、退款（可先 mock，后接支付） | P2 |
| 12 | 数据分析 | 留存/活跃/转化趋势图 | P2 |

### 2.2 角色与权限（建议先粗后细）

| 角色 | 范围 | 说明 |
|---|---|---|
| 超级管理员 | 全部 | 首个 `is_admin` 用户；可管理其他管理员 |
| 运营 | 用户查看、内容审核、公告、积分调整（需审计） | 日常运营 |
| 财务 | 套餐定价、模型单价、成本/收入报表（只读为主） | 不碰用户封禁 |
| 客服 | 用户查看、积分调整、封禁 | 处理工单 |

> MVP 阶段可只用 `is_admin` 布尔 + 审计日志；P2 再细分为上表角色（新增 `admin_role` 字段或 `admin_users` 表）。

### 2.3 关键业务流程

- **手动调积分**：后台输入 `delta` + 必填 `reason` → 写 `users.points_balance` + 落 `usage_records`（`op_type=admin_adjust`）+ 审计日志。负数扣减下限为 0。
- **升降级套餐**：选目标等级 → 更新 `users.tier_id`；若套餐含积分包，可选「补发当月积分」或「下月生效」。老用户已购套餐建议按快照，价格改动只影响新购。
- **封禁用户**：置 `users.status=banned` → 登录态失效、禁止生成；解封可恢复。封禁需填原因并审计。
- **改套餐价格**：改 `membership_tiers.price_monthly` → 立即对新购生效；历史订单不动。
- **内容下架**：置 `documents`/`materials`/`style_profiles` 的 `status=removed` → 前台不可见，数据保留（软删除）。
- **改全局配置**：写 `global_config`（KV）→ 即时影响前端行为（如注册开关）。

## 三、技术方案

### 3.1 前端架构

- **同仓路由组**：在现有 Next.js 16 App Router 中新增 `/admin/*` 路由组（如 `app/admin/(dashboard)/page.tsx`），**复用现有设计系统**（紫色 `#534AB7`、暖灰 `#F1EFE8`、卡片/表单/按钮 token）与组件库，避免重复造轮子。
- **路由守卫**：`WritingWorkspace` 模式已有 `AuthProvider`；新增 `requireAdmin` 判断 `currentUser.is_admin`，否则重定向登录/无权限页。
- **布局**：后台独立 `AdminLayout`（左侧模块导航 + 右侧内容区），与用户端 `Sidebar` 视觉一致但模块不同。
- **通用组件（需补）**：
  - `DataTable`：分页 + 筛选 + 排序 + 行操作（复用现有 `.card`/`.usage-grid` 风格）。
  - `AdminFormModal`：新增/编辑弹窗（复用 `Modal` 体系）。
  - `StatCard`：仪表盘指标卡。
  - `ConfirmDangerDialog`：危险操作二次确认（输入确认词/填理由）。
- **数据层**：在 `lib/api.ts` 扩展 `admin` 命名空间（`listAdminUsers`、`adjustUserPoints`、`listTiers`…）；类型在 `lib/types.ts` 扩充 `AdminUser`、`AdminMetrics`、`Announcement` 等。
- **安全 UX**：积分调整、封禁、删除等级等危险操作必须二次确认 + 理由必填；批量操作禁用或限流。

### 3.2 后端：现有能力盘点（直接复用）

| 端点 | 状态 | 后台用途 |
|---|---|---|
| `GET/POST/PATCH/DELETE /v1/admin/tiers` | ✅ | 会员等级 CRUD |
| `GET/POST/PATCH/DELETE /v1/admin/article-length-brackets` | ✅ | 长度档位 CRUD |
| `GET/POST/PATCH/DELETE /v1/admin/operation-costs` | ✅ | 操作积分 CRUD |
| `GET/POST/PATCH/DELETE /v1/admin/model-pricing` | ✅ | 模型单价 CRUD |
| `GET /v1/admin/users`（分页） | ✅ | 用户列表 |
| `GET /v1/admin/users/{id}` | ✅ | 用户详情 |
| `POST /v1/admin/users/{id}/points` | ✅ | 手动调积分 |
| `GET /v1/admin/usage`（按 user/op 筛选） | ✅ | 积分消耗流水 |

### 3.3 后端：需新增 API（规划）

**聚合与仪表盘**
- `GET /v1/admin/metrics/overview` → 用户总数、今日新增、今日活跃、累计文章、本月积分消耗、本月成本、本月收入（估算）。
- `GET /v1/admin/analytics/{metric}?range=7d|30d|90d` → 时间序列（新增用户/活跃/生成量/消耗/成本）。

**用户管理增强**
- `GET /v1/admin/users?q=&tier=&status=&page=` → 按用户名/邮箱/等级/状态搜索。
- `POST /v1/admin/users/{id}/set-tier` → 升降级（含「是否补发积分」选项）。
- `POST /v1/admin/users/{id}/ban` / `/unban` → 风控封禁/解封（带 reason）。

**内容与任务**
- `GET /v1/admin/materials`、`/style-profiles`、`/documents` → 列表（含 owner、状态、时间）。
- `POST /v1/admin/documents/{id}/takedown`、`/materials/{id}/takedown` → 软下架。
- `GET /v1/admin/writing-tasks?status=` → 任务巡检（定位失败/卡住任务）。

**成本与财务**
- `GET /v1/admin/cost/summary?range=` → 按模型聚合 token 与成本、与套餐收入对比得毛利。
- `GET /v1/admin/orders`（P2，先 mock）→ 订单/续费列表。

**运营与系统**
- `GET/POST/PATCH /v1/admin/announcements` → 公告（弹窗/站内信）。
- `GET/POST/PATCH/DELETE /v1/admin/promo-codes` → 优惠码（折扣/赠送积分）。
- `GET/PUT /v1/admin/global-config` → 全局开关（注册/维护模式/默认等级）。
- `GET /v1/admin/audit-logs?actor=&target=&page=` → 操作审计。

### 3.4 数据模型扩展

| 表 | 用途 | 优先级 |
|---|---|---|
| `admin_audit_logs`（新增） | `actor_id`/`action`/`target_type`/`target_id`/`before`/`after`/`reason`/`created_at` | P0 |
| `users.status`（改字段，默认 `active`） | `active`/`banned`/`deleted` 软状态 | P0/P1 |
| `announcements`（新增） | 标题/内容/渠道(弹窗\|站内信)/生效时间/状态 | P2 |
| `promo_codes`（新增） | 码/类型(折扣\|赠积分)/值/用量上限/有效期 | P2 |
| `global_config`（新增 KV 表） | `key`/`value`/`description` | P1 |
| `subscriptions` / `billing_orders`（新增，先 mock） | 订单/续费/退款 | P2 |
| `content_reports`（新增，可选） | 举报人/对象/原因/处理状态 | P2 |

### 3.5 安全与合规
- `require_admin` 已存在；新增**审计中间件**：对所有 `POST/PATCH/DELETE /v1/admin/*` 自动写 `admin_audit_logs`（操作人、前后值、理由）。
- **危险操作分级**：删除等级、封禁、下架内容 → 强制理由 + 二次确认；批量操作限流。
- **审计日志不可篡改**：只追加，无删除/编辑接口。
- **敏感字段脱敏**：用户列表不返回密码哈希；导出含 PII 时加权限校验。

### 3.6 实施分期（建议落地顺序）

- **P0（MVP，先交付，复用现有 API）**
  - 仪表盘（概览指标卡 + 基础计数）。
  - 用户管理：列表（增强搜索）+ 详情 + 手动调积分 + 升降级。
  - 配置管理 UI：等级 / 长度档位 / 操作积分 / 模型单价 的 CRUD（直接套现有 API）。
  - 积分消耗流水查看。
  - 基础审计日志（写入 + 查看）。
  - *覆盖用户原三块诉求 + 必要的仪表盘与审计。*

- **P1（进阶）**
  - 内容管理：素材 / 风格档案 / 文章 查看与软下架。
  - 成本管理报表（模型成本、毛利）。
  - 风控：封禁/解封、用户状态。
  - 系统配置：全局开关、维护模式。
  - 写作任务巡检。

- **P2（高级）**
  - 财务订单（真实支付对接：微信/支付宝）。
  - 优惠码 / 邀请码、公告推送。
  - 数据分析趋势图（留存/活跃/转化）。
  - 内容举报审核队列、角色细分（运营/财务/客服）。

## 四、开放问题（需你拍板后再细化）

1. **支付**：P2 财务是否接真实微信/支付宝支付，还是长期 mock？影响 `subscriptions` 表设计与订单流程。
2. **多角色**：MVP 是否只要 `is_admin` 一个开关，还是一开始就分运营/财务/客服？
3. **公告渠道**：弹窗（每次进首页）、站内信（消息中心）、还是二者都要？
4. **价格改动策略**：改套餐后，老用户按「购买时快照」还是「当前等级」？建议快照。
5. **部署隔离**：后台是否独立域名/部署（更安全的边缘鉴权），还是同一前端 `/admin` 路由组即可？

> 建议：先按 P0 落地（复用现有 API，最快出可用后台），开放问题在第 P1 启动前确认即可。
